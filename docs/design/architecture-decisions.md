# Architecture Decision Records (ADR)

이 문서는 Mercury V2 프로젝트의 주요 아키텍처 결정사항을 기록합니다.

## ADR-001: 비동기 작업 처리 방식 (Celery + Redis)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
AI 이미지 생성은 시간이 오래 걸리는 작업으로, 동기 처리 시 사용자 경험이 저하됩니다.

### 결정
**Celery + Redis**를 비동기 작업 처리에 사용합니다.

### 근거
- **검증된 솔루션**: Python 생태계에서 가장 널리 사용되는 Task Queue
- **확장성**: Worker 수평 확장 용이
- **모니터링**: Flower 등 모니터링 도구 지원
- **재시도 로직**: 내장된 재시도 및 에러 핸들링

### 대안
- FastAPI BackgroundTasks: 간단하지만 확장성 제한
- AWS SQS/Lambda: 클라우드 종속성 증가

## ADR-002: 파일 스토리지 (AWS S3)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
생성된 이미지 파일을 안정적이고 확장 가능하게 저장해야 합니다.

### 결정
**AWS S3**를 파일 스토리지로 사용하며, Pre-signed URL로 보안을 강화합니다.

### 근거
- **확장성**: 무제한 스토리지
- **내구성**: 99.999999999% 내구성 보장
- **보안**: Pre-signed URL로 시간 제한 접근 제어
- **CDN 통합**: CloudFront와 쉽게 통합 가능

### 대안
- 로컬 파일 시스템: 확장성 제한, 백업 복잡
- MinIO: 자체 호스팅 필요, 운영 부담

## ADR-003: 캔버스 Undo/Redo 전략 (프론트엔드 관리)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
캔버스 작업의 Undo/Redo 기능을 구현하기 위해 히스토리 저장 방식을 결정해야 합니다.

### 결정
**프론트엔드 메모리에서만 히스토리를 관리**하며, DB에는 저장하지 않습니다.

### 근거
- **구현 단순성**: 프론트엔드 상태 관리로 충분
- **서버 부하 감소**: 모든 액션을 DB에 저장할 필요 없음
- **성능**: 네트워크 왕복 없이 즉각적인 Undo/Redo
- **MVP 적합**: 초기 단계에서는 단일 사용자 환경

### 트레이드오프
- 새로고침 시 히스토리 손실 (사용자에게 명확히 안내)
- 추후 협업 기능 추가 시 서버 기반 히스토리 저장 재검토 필요

### 대안
- DB 저장: 세션 복원 가능하지만 서버 부하 증가
- 하이브리드: 최근 N개만 DB 저장 (복잡도 증가)

## ADR-004: 실시간 통신 방식 (SSE 통일)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
채팅 스트리밍, 이미지 생성 상태 업데이트 등 실시간 통신이 필요합니다.

### 결정
**Server-Sent Events (SSE)**로 모든 실시간 통신을 통일합니다. WebSocket은 사용하지 않습니다.

### 근거
- **단방향 통신 충분**: 서버 → 클라이언트 업데이트만 필요 (클라이언트는 REST API 사용)
- **HTTP/2 호환성**: 멀티플렉싱으로 여러 SSE 연결을 효율적으로 처리
- **구현 단순성**: WebSocket보다 간단 (연결 관리, 재연결 로직)
- **인프라 친화적**: 로드 밸런서, 프록시 통과 용이
- **자동 재연결**: 브라우저 EventSource API가 자동 재연결 지원

### 트레이드오프
- 양방향 실시간 통신 불가 (추후 협업 기능 시 WebSocket 재검토)

### 인프라 요구사항
- **HTTP/2 필수**: Nginx/Caddy에서 HTTP/2 활성화

## ADR-005: AI 이미지 생성 (외부 API 사용)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
신발 디자인 이미지를 생성하기 위한 AI 모델이 필요합니다.

### 결정
**외부 AI API**(Google Imagen, Stability AI 등)를 사용하며, **동적 모델 선택**을 지원합니다.

### 근거
- **운영 부담 감소**: GPU 인프라 관리 불필요
- **최신 모델 접근**: 외부 제공자가 모델 업데이트 관리
- **비용 효율성**: 사용량 기반 과금 (초기 투자 불필요)
- **유연성**: 여러 모델 중 선택 가능

### 구현 방식
- 요청 시 `model` 파라미터로 모델 지정
- 예시: `gemini-3-pro-image-preview`, `stable-diffusion-xl-1024-v1-0`, `dall-e-3`

### API 호출 흐름
```
클라이언트 → FastAPI → Celery Task → 외부 AI API → S3 업로드 → DB 저장 → SSE 알림
```

### 대안
- 자체 GPU 서버: 초기 투자 비용 높음, 운영 복잡
- 클라우드 GPU (SageMaker): 외부 API보다 복잡, 비용 예측 어려움

## ADR-006: Segmentation 모델 (추후 개발, 외부 API)

**날짜**: 2026-01-21  
**상태**: 계획됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
캔버스 내 이미지 객체 선택 시 자동 세그멘테이션 기능이 필요합니다.

### 결정
**별도 외부 AI 모델 서버**(SAM, Segment Anything 등)를 사용합니다.

### 근거
- **전문화**: 이미지 생성과 세그멘테이션은 별도 모델
- **외부 API 활용**: 자체 호스팅 부담 감소
- **확장성**: 추후 다른 비전 모델 추가 용이

### 호출 방식
```
FastAPI → 외부 Segmentation API → 결과 반환 (마스크 데이터)
```

## ADR-007: 마케팅 리포트 생성 (LangGraph)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
디자인 패키지의 마케팅 리포트는 시장 분석, 비용 분석, 트렌드 분석 등 복잡한 과정을 거칩니다.

### 결정
**LangGraph**를 사용하여 각 단계를 노드로 관리하는 구조화된 워크플로우를 구현합니다.

### 근거
- **복잡한 워크플로우 관리**: 각 분석 단계를 명확히 분리
- **디버깅 용이**: 각 노드의 입출력 추적 가능
- **확장성**: 새로운 분석 단계 추가 용이
- **재사용성**: 노드 단위로 재사용 가능

### 워크플로우 예시
```
collect_requirements → analyze_market → estimate_cost → generate_chart_data → finalize_report
```

### 각 노드 역할
- `collect_requirements`: 디자인 메타데이터 수집
- `analyze_market`: LLM으로 시장 분석 생성
- `estimate_cost`: LLM으로 비용 추산
- `generate_chart_data`: 시각화용 데이터 생성
- `finalize_report`: 최종 리포트 조합

### 대안
- 단일 LLM 호출: 복잡도 높고 디버깅 어려움
- 외부 데이터 연동: MVP 단계에서 불필요한 복잡성

## ADR-008: JWT 인증 전략 (MVP: Access Token만)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
사용자 인증 및 세션 관리 방식을 결정해야 합니다.

### 결정
MVP 단계에서는 **Access Token만 사용** (24시간 만료)하며, Refresh Token은 추후 도입합니다.

### 근거
- **구현 단순성**: MVP에서는 기능 동작 우선
- **단일 사용자 환경**: 보안 요구사항 상대적으로 낮음
- **빠른 개발**: Refresh Token 로직 생략으로 개발 속도 향상

### 추후 계획
- Refresh Token 도입 (보안 강화)
- 토큰 만료 시간 단축 (Access Token: 1시간, Refresh Token: 30일)

## ADR-009: JSONB 인덱싱 전략 (필요 시 추가)

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
JSONB 컬럼에 GIN 인덱스를 추가하면 검색 성능이 향상되지만 쓰기 성능이 저하됩니다.

### 결정
**초기에는 JSONB 컬럼에 인덱스를 추가하지 않으며**, 성능 이슈 발생 시 추가합니다.

### 근거
- **조기 최적화 방지**: MVP 단계에서는 불필요
- **쓰기 성능 우선**: 이미지 생성 시 메타데이터 저장 빈번
- **측정 후 최적화**: 실제 사용 패턴 파악 후 결정

### 모니터링 지표
- JSONB 컬럼 검색 쿼리 응답 시간
- 사용자 불만 사항

## ADR-010: HTTP/2 인프라 요구사항

**날짜**: 2026-01-21  
**상태**: 승인됨  
**결정자**: 시스템 아키텍트

### 컨텍스트
SSE를 효율적으로 사용하기 위해 인프라 레벨에서 HTTP/2를 지원해야 합니다.

### 결정
**리버스 프록시(Nginx/Caddy)에서 HTTP/2를 활성화**합니다.

### 근거
- **멀티플렉싱**: 여러 SSE 연결을 단일 TCP 연결에서 처리
- **성능 향상**: 헤더 압축, 서버 푸시 등
- **브라우저 지원**: 모든 모던 브라우저가 HTTP/2 지원

### 구현 방법
**Nginx 예시**:
```nginx
server {
    listen 443 ssl http2;
    # ... SSL 설정
}
```

**Caddy 예시**:
```
example.com {
    # Caddy는 기본적으로 HTTP/2 활성화
}
```

## ADR-011: LLM 통합 라이브러리 (LiteLLM)

**날짜**: 2026-01-22  
**상태**: 승인됨  
**결정자**: 백엔드 개발팀

### 컨텍스트
채팅 기반 디자인 생성을 위해 LLM API 연동이 필요하며, 향후 다양한 모델로 전환할 수 있는 유연성이 요구됩니다.

### 결정
**LiteLLM** 라이브러리를 사용하여 LLM API를 통합합니다.

### 근거
- **다중 제공자 지원**: OpenAI, Anthropic, Google, Azure 등 100+ 모델을 통일된 인터페이스로 사용
- **확장성**: 모델 변경 시 코드 수정 최소화 (설정만 변경)
- **비용 최적화**: 여러 제공자 간 성능/비용 비교 및 전환 용이
- **스트리밍 지원**: SSE 스트리밍 응답 완벽 지원
- **프로덕션 준비**: 안정적이고 활발히 유지보수됨

### 사용 예시
```python
import litellm

# OpenAI 사용
response = await litellm.acompletion(
    model="gpt-4-turbo-preview",
    messages=[{"role": "user", "content": "Hello"}],
    stream=True
)

# 다른 모델로 쉽게 전환 (코드 변경 없음)
response = await litellm.acompletion(
    model="claude-3-opus-20240229",  # Anthropic
    messages=[{"role": "user", "content": "Hello"}],
    stream=True
)
```

### 대안
- **openai**: OpenAI 전용, 다른 제공자로 전환 시 코드 전면 수정 필요
- **langchain**: 복잡한 워크플로우에 적합하지만 단순 채팅에는 과함
